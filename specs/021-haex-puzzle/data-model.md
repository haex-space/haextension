# Data Model: haex-puzzle

Phase 1 of [plan.md](plan.md). Two kinds of data: the **library** (persistent, in the vault) and the **puzzle** (in memory, gone when the extension closes — spec Assumptions).

## Persistent: table `pictures`

One Drizzle table in `app/database/schemas/index.ts`, named with the repository's prefix helper (`getTableName(publicKey, "haex-puzzle", "pictures")`, as in `apps/haex-doom/app/database/schemas/index.ts`). Not suffixed `_no_sync`: the library is synced between the user's devices (research R-4).

| Column | Type | Notes |
|--------|------|-------|
| `id` | text, primary key | Lowercase hex SHA-256 of the **original file's bytes**. The same file added on two devices is the same row, so a sync never sees two rows for one picture; it is also the duplicate check (FR-026, R-3). |
| `name` | text, not null | The original file's name without its folder; shown under the thumbnail. |
| `width`, `height` | integer, not null | Pixel size of the stored copy (after downscaling and orientation). |
| `mime_type` | text, not null | `image/webp` or `image/jpeg`, whichever encoder produced `data`. |
| `data` | blob, not null | The stored copy, at most 1 MiB (R-2). The only column a puzzle needs. |
| `thumbnail` | blob, not null | WebP/JPEG, long side 256 px, typically 8–25 KB. |
| `added_at` | text, not null | ISO 8601 UTC; the library lists newest first. |

**Index**: the primary key on `id`; no other index.

**Rules**

- A row is complete or absent: it is inserted with one `INSERT … ON CONFLICT (id) DO NOTHING` and removed with one `DELETE … WHERE id IN (…)` (all or nothing), so there is never a thumbnail without a picture or the reverse (FR-027).
- The list query selects **every column except `data`**, so opening the start screen never moves the pictures themselves (FR-024). `data` is read for one picture when its puzzle starts.
- `data` is never modified after the insert; there is no update path (the library has no renaming, spec Assumptions).
- Validation at the door (before the insert): file ≤ 64 MiB; decoded size ≤ 100 MP; Easy available at the stored size (≥ ~84 × 84 px); the encoded copy ≤ 1 MiB; otherwise a typed rejection (below), nothing stored.

**State**: none beyond present/absent. A row whose `data` can no longer be decoded is shown as unusable (spec edge case) by the failed decode at puzzle start, not by a stored flag; the thumbnail column keeps the entry visible and removable.

**Migration**: `app/database/migrations/0000_*.sql` generated by `drizzle-kit generate`, plus its `meta/` snapshot, registered at start with `client.registerMigrationsAsync` (R-12). No data migration; the table is new.

## In memory: Puzzle

All coordinates are pixels of the stored picture. None of these types is persisted.

### Difficulty (constant list in `app/lib/difficulty.ts`)

| Field | Type | Notes |
|-------|------|-------|
| `id` | `'easy' \| 'medium' \| 'hard' \| 'expert'` | |
| `target` | number | 12, 48, 108, 192. |
| `minPieceSide` | number | 24 px, the availability rule of R-5. |

### Grid (derived, `app/lib/grid.ts`)

| Field | Type | Notes |
|-------|------|-------|
| `columns`, `rows` | number | Product within ±10 % of the difficulty's target. |
| `pieceWidth`, `pieceHeight` | number | `width / columns`, `height / rows`; fractional, the last column/row is not special: piece `(c, r)` covers `[c·pw, (c+1)·pw] × [r·ph, (r+1)·ph]`. |

### Edge (derived, `app/lib/jigsaw.ts`)

| Field | Type | Notes |
|-------|------|-------|
| `direction` | `1 \| -1` | Which of the two neighbours carries the tab. |
| `shape` | `{ tab, neck, shoulder, lean }` | Fractions of the edge length, each varied within a small range from the seed. |

Held in a `columns × (rows − 1)` array of horizontal edges and a `(columns − 1) × rows` array of vertical ones; the outer sides of the picture have no edge entry and are straight.

### Piece

| Field | Type | Notes |
|-------|------|-------|
| `id` | number | `row × columns + column`. |
| `column`, `row` | number | Home cell. |
| `x`, `y` | number | Current top-left of the piece's cell box on the table; at home when `x = column × pw`, `y = row × ph`. |
| `group` | number | Id of the group the piece belongs to. |

### Group

| Field | Type | Notes |
|-------|------|-------|
| `id` | number | |
| `pieceIds` | number[] | At least one. A group's pieces keep their relative offsets. |
| `placed` | boolean | True once the group snapped to the frame; a placed group is never dragged or hit-tested. |
| `z` | number | Stacking order; a released group gets the highest value. |

### PuzzleState

| Field | Type | Notes |
|-------|------|-------|
| `pictureId` | string | The library row the puzzle was cut from. |
| `difficulty` | Difficulty id | |
| `grid` | Grid | |
| `pieces` | Piece[] | |
| `groups` | Group[] | |
| `phase` | `'playing' \| 'complete'` | There is no `idle` state here: the start screen is the absence of a puzzle. |
| `elapsedMs` | number | From the stopwatch; frozen at completion. |

**Transitions** (`app/lib/puzzleState.ts`)

- `start(picture, difficulty, random)` → pieces scattered (R-10), every piece its own group, none placed, `phase = playing`.
- `release(groupId, delta)` → apply the move, clamp into the table, then snap-to-home or join (R-9); `phase = complete` when every group is placed and only one group remains.
- `restartSame(random)` → the same picture and grid, a new scatter, elapsed reset.

**Invariants** (asserted by tests)

1. Every piece is in exactly one group; a group's pieces are pairwise connected through grid neighbours.
2. A placed group's pieces are exactly at their homes.
3. Within a group, the offset between two pieces equals the difference of their homes.
4. `complete` ⇔ one group holding all pieces, placed.
5. At least one piece of every loose group lies within the table.

## Library listing item (what the start screen holds)

| Field | Type | Notes |
|-------|------|-------|
| `id`, `name`, `width`, `height`, `addedAt` | as above | |
| `thumbnail` | `Uint8Array` | Turned into an object URL by the thumbnail component, revoked on removal and on unmount. |

## Rejections (typed, shown as messages)

`unsupported` (cannot be decoded), `too-large` (> 64 MiB or > 100 MP), `too-small` (below Easy), `storage-failed` (the vault refused the write), `read-failed` (the host could not read the file). A multi-file add collects these and shows one message (US3 scenario 8). `duplicate` is not an error: the existing entry is returned.
